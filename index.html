Trabajo de Fin de Grado en colaboración con Facephi Bachelor's thesis in collaboration with Facephi

Validar un DNI a partir de dos fotografías Validating a Spanish ID card from two photos

Sistema que comprueba un DNI español a partir de una foto de cada cara: lee los campos por OCR, valida la MRZ, cruza los datos del anverso con los del reverso y devuelve válido, inválido o revisión manual. Encima monté una capa en LangGraph que decide cuándo usar herramientas de apoyo, y da los mismos veredictos que usarlas siempre con un 43 % menos de ejecuciones. También creé un conjunto de 27 DNI sintéticos con alteraciones de campos para usarlos como casos adversariales en la evaluación. TFG propuesto con Facephi.

A system that checks a Spanish ID card (DNI) from one photo of each side: it reads the fields with OCR, validates the MRZ, cross-checks the front against the back and returns valid, invalid or manual review. On top of it I built a LangGraph layer that decides when to use support tools; it gives the same verdicts as always using them, with 43% fewer runs. I also created a set of 27 synthetic ID cards with altered fields to use as adversarial cases in the evaluation. Thesis proposed with Facephi.

Trabajo de Fin de Grado propuesto en colaboración con Facephi. Partiendo solo de una foto del anverso y otra del reverso de un DNI español, el sistema lee los campos por OCR, recalcula los dígitos de control de la MRZ según la norma ICAO 9303 y cruza los datos de las dos caras en 11 verificaciones. Puede responder válido, inválido o revisión manual. Este último lo diseñé para que un caso dudoso acabe en manos de una persona y el sistema no lo decida a ciegas. Para evaluarlo generé 27 DNI sintéticos con campos alterados: una letra del NIF que no cuadra con los dígitos, un dígito de control de la MRZ modificado, un nombre distinto en cada cara. Cada uno debería hacer saltar una verificación concreta.

Bachelor's thesis proposed in collaboration with Facephi. Starting from just a photo of the front and one of the back of a Spanish ID card, the system reads the fields with OCR, recomputes the MRZ check digits following ICAO 9303 and cross-checks both sides in 11 verifications. It can answer valid, invalid or manual review. I designed the last one so that a doubtful case ends up with a person instead of the system deciding blindly. To evaluate it I generated 27 synthetic ID cards with altered fields: an NIF letter that doesn't match its digits, a modified MRZ check digit, a different name on each side. Each one should trigger a specific check.

Sobre esa base construí una capa de orquestación con LangGraph. Decide cuándo compensa pasar un filtro de calidad de imagen o releer un campo concreto. La comparé en 54 documentos degradados con no usar nunca esas herramientas y con usarlas siempre: dio los mismos veredictos que usarlas siempre, con 155 ejecuciones de apoyo en vez de 270 (un 43 % menos). Las tres configuraciones comparten el código que emite el veredicto, así que la diferencia solo puede venir de la política, y por eso sé que lo que mejora es el coste y no el acierto.

On top of that base I built an orchestration layer with LangGraph. It decides when it's worth running an image-quality filter or re-reading a specific field. I compared it on 54 degraded documents against never using those tools and always using them: it gave the same verdicts as always using them, with 155 support runs instead of 270 (43% fewer). All three configurations share the code that issues the verdict, so the difference can only come from the policy, which is how I know that what improves is the cost, not the accuracy.

Para enseñarlo diseñé también una interfaz web. Subes las dos caras, eliges la configuración y ves cómo avanza el grafo paso a paso, con las verificaciones en tiempo real.

To show it, I also designed a web interface. You upload both sides, choose the configuration and watch the graph progress step by step, with the checks in real time.

Universidad de WaikatoUniversity of Waikato, Machine Learning for Data Streams, 2025, equipo de seisteam of six

Predicción de ocupación de autobuses en tiempo realReal-time bus crowding forecasting

Con datos de diez paradas de Salvador (Brasil) predecimos la ocupación media de los siguientes 30 minutos, usando modelos que aprenden a medida que llegan los datos. Comparamos enfoques autorregresivos, la codificación de hora y parada y variables de contexto con KNN, FIMT-DD y Adaptive Random Forest; además montamos un prototipo que propone paradas alternativas cuando se prevé saturación.

Using data from ten bus stops in Salvador (Brazil), we forecast average crowding for the next 30 minutes with models that learn as the data arrives. We compared autoregressive approaches, time and stop encodings and contextual features with KNN, FIMT-DD and Adaptive Random Forest, and built a prototype that suggests alternative stops when crowding is expected.

Mi parte: planteamiento, metodología, software y redacción del artículo, y el desarrollo y la evaluación del modelo de referencia basado en hora y parada. El mejor modelo bajó el MAE de 7,43 a 6,24 frente a la referencia ingenua.

My part: conceptualisation, methodology, software and writing of the paper, plus building and evaluating the time-and-stop baseline. The best model cut MAE from 7.43 to 6.24 against the naive baseline.

Lo que aprendí: en lo técnico, a trabajar con modelos que aprenden mientras llegan los datos y a comprobar si de verdad mejoran frente a una referencia sencilla. En lo personal, fue mi primer proyecto en un equipo internacional de seis personas y en inglés: al principio me costó que mis propuestas se escucharan, y eso me obligó a explicarlas mejor y a construir sobre las ideas de los demás.

What I learned: technically, how to work with models that learn as the data arrives, and how to check whether they really beat a simple baseline. Personally, it was my first project in an international team of six, working in English: at first it was hard to get my proposals heard, which pushed me to explain them better and to build on other people's ideas.

Buscador de artículos académicosAcademic paper search engine

Un motor de búsqueda local sobre literatura de verificación documental, desinformación y fiabilidad de los modelos de lenguaje. Recoge metadatos de OpenAlex, construye un índice invertido y acepta búsquedas booleanas (AND, OR, NOT y paréntesis) ordenadas por TF-IDF. En la entrega indexé 615 artículos y medí la calidad de los resultados con 12 consultas de prueba.

A local search engine over literature on document verification, misinformation and LLM reliability. It collects metadata from OpenAlex, builds an inverted index and supports Boolean queries (AND, OR, NOT and parentheses) ranked with TF-IDF. The submitted version indexed 615 papers, and I measured the quality of its results with 12 test queries.

Mi parte: todo el proyecto, de la recogida de datos a la evaluación. Más tarde le añadí una interfaz web en Python para poder probarlo sin abrir Colab.

My part: the whole project, from data collection to evaluation. Later I added a Python web interface so it can be tried without opening Colab.

Lo que aprendí: a orientar un trabajo de clase hacia mis propios objetivos: elegí un tema cercano a mi TFG y después usé el buscador para encontrar referencias para la memoria. En lo técnico, que los datos de una API real casi nunca llegan listos (tuve que reconstruir los resúmenes de OpenAlex y limpiar el conjunto antes de indexar) y que coincidir en palabras no es coincidir en significado.

What I learned: to steer a class assignment towards my own goals: I chose a topic close to my thesis and later used the search engine to find references for it. Technically, that data from a real API rarely arrives ready to use (I had to rebuild OpenAlex's abstracts and clean the set before indexing) and that matching words is not the same as matching meaning.

Universidad de AlicanteUniversity of Alicante, Sistemas Distribuidos, 2024–2025, en pareja con Levan Kipianiwith Levan Kipiani

EasyCab, flota de taxis distribuidadistributed taxi fleet

Un simulador en el que clientes, una central y los taxis se comunican mediante Kafka y sockets TCP. Tiene sensores en los vehículos, control meteorológico a través de APIs Flask y el mapa de la flota se puede seguir en Pygame o en una web hecha con Astro. Lo desplegamos a la vez en tres ordenadores distintos.

A simulator where customers, a central server and taxis talk to each other over Kafka and TCP sockets. It has vehicle sensors, weather control through Flask APIs, and the fleet map can be followed in Pygame or in an Astro web view. We deployed it across three different computers at once.

Mi parte: la visualización de la flota, con el mapa en Pygame, la web en Astro y la API que le pasa el estado del mapa; el módulo de clientes, y buena parte de la central y del motor de los taxis junto a Levan. También preparé el despliegue final y resolví los conflictos al juntar nuestras ramas.

My part: the fleet visualisation, with the Pygame map, the Astro web view and the API that feeds it the map state; the customer module, and a good share of the central server and the taxi engine together with Levan. I also prepared the final deployment and resolved the conflicts when merging our branches.

Lo que aprendí: que en un sistema distribuido muchos fallos no están en tu código. Con Kafka tuvimos que lidiar con mensajes que no llegaban en el orden esperado, y desplegarlo en los ordenadores de la universidad, configurando la red de Kafka para que todos los equipos se vieran, nos costó tanto como programarlo. Me llevo paciencia para depurar: aislar el fallo, probar componente a componente y no dar nada por hecho.

What I learned: that in a distributed system many failures aren't in your code. With Kafka we had to deal with messages that didn't arrive in the expected order, and deploying it on the university computers, configuring Kafka's networking so every machine could see the others, took as much effort as writing it. I came away with patience for debugging: isolating the fault, testing component by component and taking nothing for granted.
